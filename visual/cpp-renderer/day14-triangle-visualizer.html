01为什么全世界的模型只存三角形

立方体明明用 6 个四边形拼更省事，可 OBJ、FBX、glTF 里一个四边形都找不到。

三条理由，最后一条是硬约束：

  1. 三点永远共面。任意 4 个空间点凑"四边形"，可能不共面 —— 像一张被扭过的纸。"这个面朝哪"就没有唯一答案。
  2. 任意多边形都能切成三角形。五边形、带洞的形状，都有现成算法（耳切法、单调剖分）。反过来不成立：三角形切不出别的。
  3. 硬件只认三角形。GPU 图元装配单元只接受点 / 线 / 三角形。你提交四边形，是驱动在背后替你拆。

把"共面"算清楚

取三点 A、B、C，记 u = B − A、v = C − A、n = u × v。若 n ≠ 0（三点不共线），那么过这三点的平面唯一：

三点定平面 { P : n · (P − A) = 0 }

第四个点 D 在这个平面上，当且仅当一个标量等式成立：

共面判据 n · (D − A) = 0   ⟺   det(u, v, D − A) = 0 （混合积 = 三向量张成的平行六面体体积，体积为零就是共面）

这是一个可以随便不成立的等式。一旦不成立，四边形就有两条互不相容的对角线：沿 b–c 拆，得到两个法线 n₁, n₂；沿 a–d 拆（d 是第 4 个点），得到另外两个 n₃, n₄。四个法线一般互不相同 —— 于是"这个面的法线是多少"的答案，变成了你的实现细节。而三角形连"选哪条对角线"这个问题都不存在。

设计判断
形状的属性不该依赖于"我选择怎么拆"。三角形没有这个问题：它的法线是被三个顶点唯一决定的。 所以整个图形学把"面"这个概念的唯一真身定为三角形，四边形只是建模时的手感。

拖动右侧滑块，把第 4 个点抬离平面，看两条对角线拆出来的法线怎么劈叉。滑块归零时它们重新重合 —— 那一刻四个点共面，四边形才是一个"平面图形"。

读动画
蓝色是拆法 ①（对角线 b–c）的两个三角形法线； 紫色是拆法 ②（对角线 a–d）。 同一种颜色的两条法线之间的夹角，就是"这个面朝哪"的不确定度。

02整个 Triangle 类：一个构造函数 + 一个虚函数

不重写 hit()、不重写 bounding_box()、不重算平面参数。只覆盖一处。

include/triangle.h · 全文（去掉注释） 
class Triangle : public Quad {public:    Triangle(const Point3& a, const Point3& b, const Point3& c,             std::shared_ptr<Material> mat)        : Quad(a, b - a, c - a, mat) { }   // ← 空 1：两条边向量    bool is_interior(double alpha, double beta) const override {        return alpha >= 0 && beta >= 0 && alpha + beta <= 1;  // ← 空 2    }};

空 1：b - a 是向量，b 是位置

Quad 的构造签名是 Quad(Q, u, v, mat)，其中 u、v 是边向量，不是顶点。三角形给的是三个顶点，所以必须做一次减法：位置 − 位置 = 向量。

为什么不能直接把 b、c 塞进去？因为 b 表示的是"从原点指向 b 的向量"，只有当 a 恰好落在原点时，b = b − a 才偶然成立。这个 bug 极其阴险：顶点在原点的那条测试会通过，看起来"没问题"（§8 有完整解剖）。

空 2：virtual 是怎么找到子类的

Quad::hit() 里那句 if (!is_interior(alpha, beta)) return false; 调用的是基类里声明为 virtual 的函数。通过指针调用虚函数时，编译器不写死地址，而是查对象里的 vptr → 查 vtable，找到的永远是对象真实类型的版本：

Quad::hit(r, t_min, t_max, rec) 平面求交 → 算 α, β → 调 is_interior
▶
Triangle::is_interior(a, b) return a >= 0 && b >= 0 && a + b <= 1;

同一份求交代码，配 Quad::is_interior 就是四边形，配 Triangle::is_interior 就是三角形。这就是多态的全部内容 —— 不是语法糖，它把"几何体的差异"压缩成了一个 bool。

判定区域：一块方块被一条直线切掉一半

把 (α, β) 看成一张二维坐标纸。四边形要的是整个单位方块 0 ≤ α ≤ 1, 0 ≤ β ≤ 1；三角形要的是方块里被直线

一条直线切掉一半 α + β = 1  ⇒  α ≥ 0, β ≥ 0, α + β ≤ 1

切出来的那块三角区域。几何上，这条直线对应的正是平行四边形从 Q 出发的那条对角线。右上角被切掉的那半块，就是 §5 里"不存在的第四个角"所在的区域。

读动画
切换 Quad / Triangle，同一个 (α, β) 点会在"内部"与"外部"之间翻转。 偏红的那块是 α + β > 1 的被切掉区域： 它属于四边形，不属于三角形。
重心坐标 · 两个数字编号一个面

03α、β 的真正名字：重心坐标

三角形内每一点，都能被三个加起来等于 1 的权重唯一表示。

把 Quad 的参数化原样搬过来，代入 Q = a、u = b − a、v = c − a：

重心坐标 P = a + α(b − a) + β(c − a)   = (1 − α − β)·v0 + α·v1 + β·v2 其中 v0 = a, v1 = b, v2 = c

三个顶点的权重分别是

顶点权重在三角形上的位置对面小三角形
v0 = aw0 = 1 − α − βα = β = 0 时 w0 = 1(b, P, c)
v1 = bw1 = αα = 1 时 w1 = 1(a, P, c)
v2 = cw2 = ββ = 1 时 w2 = 1(a, b, P)

为什么"在三角形内"就等价于三个权重非负？因为 w0 + w1 + w2 = 1 恒成立。点在三角形里 ⟺ 它是三个顶点的凸组合 ⟺ 三个权重都 ≥ 0。把 w0 = 1 − α − β ≥ 0 移项，就得到代码里那一行：alpha >= 0 && beta >= 0 && alpha + beta <= 1。

顺便回答一个常见的困惑：三角形有 3 个顶点，为什么只有 2 个数？因为第三个权重被"和为 1"约束掉了。3 个权重 − 1 个约束 = 2 个自由度，正好对应平面上的 2 个坐标。

α 是一个面积比

从 §5 的叉积公式出发（Day 13 已推过）：

叉积消元 p = P − a = αu + βv p × v = α(u × v) + β(v × v) = αn |p × v| = α |n| 因为 |p×v| = 2·面积(a,P,c)，|n| = 2·面积(a,b,c)，2 约掉
重心坐标 = 面积比 α = 面积(a, P, c)面积(a, b, c)    β = 面积(a, b, P)面积(a, b, c)

权重 = 对面那块小三角形占总面积的比例。P 越靠近 b，b 对面的那块（a,P,c）越大，α 越大 —— 权重 1 落在 b 上，物理直觉完全一致。

为什么这个视角重要：插值

顶点上除了位置，还能挂任何属性。三角形内任意点的属性，用同一组权重插值：

重心插值（后面几十天都在用它） attr(P) = w0·attr(v0) + w1·attr(v1) + w2·attr(v2)
  • 顶点法线 → 光滑着色：800 个三角形的小球看起来像完美的球，而不是多面体
  • 顶点 UV → 贴图坐标，纹理跟着三角形一起变形
  • 顶点颜色 → 渐变（Gouraud 着色）
  • 顶点位移 → 骨骼动画、形变动画
读动画
拖动 α、β。三块彩色区域是三个子三角形，它们的面积占比就是三个权重的数值。 虚线的折角是分解路径：先沿 u 走 α，再沿 v 走 β。

04射线打到三角形：代码和四边形是同一份

它没有"三角形的求交算法"。它只有 Quad 的求交算法，加一个 false。

回放一下 Quad::hit() 的三步。每一步一步都还在，唯一的分叉出现在最后一步：

05三角形的包围盒，比三角形本身大一倍

这是继承带来的第一个"退化但不坏"的行为。

Quad 的包围盒用两个对角点扫出一个盒子：Q 与 Q+u+v 一个，Q+u 与 Q+v 另一个，取并集。三角形继承构造函数，u = b−a、v = c−a，于是：

幽灵角 Q + u + v = a + (b − a) + (c − a) = b + c − a 这个点不在三角形上。它是平行四边形被切掉的那半个角的顶点。

所以 Triangle 的包围盒 = 它所在平行四边形的包围盒。平行四边形的面积是三角形的两倍（被对角线平分），包围盒自然也跟着偏大。

为什么这不算错

Day 13 的铁律，今天继续用 包围盒宁可偏大，绝不能偏小。 偏大 → 多进几个叶子节点，慢一点点；偏小 → 漏掉命中，画面直接错。

包围盒的唯一职责是剪枝：盒子不相交就一定不命中。它从不参与"是否命中"的最终判断，所以偏大只是"剪得不够狠"，绝不会误伤。

方案图元数包围盒200 spp 渲染
6 个 Quad / 立方体18零厚度（padding 到 1e-4）2.93 s
12 个 Triangle / 立方体36等于平行四边形，大一倍4.48 s

三个立方体 + 地面。慢 53%，两个原因叠加：图元数翻倍（每个面要测两次）+ 包围盒更大（剪枝更松）。

但这是几十个图元的玩具场景。真实模型是几十万三角形 —— 那时候"四边形省一半图元"的收益，远远比不上"三角形能表示任意形状"的能力。

06退化三角形：NaN 能让所有 if 全部失效

真实 OBJ 文件里到处是面积为零的三角形 —— 重合顶点、共线三点。建模软件导出时留下的。

如果 u ∥ v（或其中一条是零向量），叉积是零向量，接着整条链子塌掉：

0/0 n = u × v = 0  ⇒  n̂ = n/|n| = 0/0 = NaN D = n̂ · Q = NaN     w = n/(n·n) = NaN

NaN 的两道防线，一道都拦不住

看 hit() 里那两个本该救命的判断：

NaN 穿透示意 · IEEE 754
denom = dot(n̂, d);          // NaNif (|fabs(denom) < 1e-8) return false;   // fabs(NaN) < 1e-8 → false，拦不住t = (D - dot(n̂, O)) / denom;  // NaNif (t <= t_min || t >= t_max) return false; // NaN ≤ x 是 false，NaN ≥ x 也是 false → 拦不住is_interior(NaN, NaN)          // NaN ≥ 0 是 false → 侥幸在这里被拦住

IEEE 754 规定：任何涉及 NaN 的比较都返回 false（只有 != 返回 true）。所以 NaN < 1e-8 是 false，NaN <= t_min 是 false。所有"把坏值挡在门外"的检查，遇到 NaN 会集体失效。

结论
唯一的办法是在产生 NaN 之前就拦住它。所以退化保护必须放在构造函数里， 用一个 degenerate 标志，让 hit() 第一步就 return false。 靠下游的 if 兜底是运气，不是设计。
include/quad.h · 构造函数里的退化保护 
Vec3 n = cross(u, v);double len2 = dot(n, n);   // = |u|²|v|² sin²θ   （长度⁴）double uu   = dot(u, u);double vv   = dot(v, v);if (len2 <= 0.0 || len2 < 1e-12 * uu * vv) {   // ← 与尺度无关    degenerate = true;    normal = Vec3(0, 1, 0);   // 给个合法值，反正 hit() 会直接 return    D = 0.0;  w = Vec3(0, 0, 0);    bbox = AABB(Q, Q);       // 退化成一个点，pad 会撑开    return;}normal = unit_vector(n);  D = dot(normal, Q);  w = n / len2;

那个 1e-12 * uu * vv 是怎么来的

第一版写的是 if (len2 < 1e-8)，被测试 C 组当场抓出来。因为量纲不对：

量纲分析 = 三秒抓 bug |n| = |u||v| sin θ  ⇒  len2 = |u|²|v|² sin²θ len2 / (uu · vv) = sin²θ   ← 只与夹角有关，与大小无关

len2 是长度的四次方。两条垂直边、边长都是 e 时 len2 = e⁴。于是 len2 < 1e-8 等价于 e < 0.01：

边长 elen2 = e⁴错误判据 len2 < 1e-8后果
2 （立方体）16正常✅
0.02 （5 万面）1.6e-7正常✅ 侥幸
0.011e-8临界⚠️
0.005 （20 万面）6.25e-10判为退化❌ 整个模型静默消失

不崩溃、不报错、不 NaN，物体只是"没了"。这是最难查的一类 bug。

正确判据把裸常数换成了同量纲的量 uu·vv（也是长度⁴）：

尺度不变 len2 < 1e-12 · uu · vv  ⟺  sin²θ < 1e-12  ⟺  θ < 10⁻⁶ rad

铁律
epsilon 必须和同量纲的量比较。判 len2（长度⁴）要用 uu·vv（也是长度⁴）， 不能拿裸常数。写 if (x < 1e-8) 之前，先问一句：x 的单位是什么？

076 个四边形 vs 12 个三角形：字节完全相同

今天真正的验收不是"看起来一样"，是 Get-FileHash 一样。

为什么必须先把"随机"从实验里踢出去

普通渲染有漫反射弹射。两张图的差别不是"几何算错了"，而是随机：第二个三角形的法线是 cross(v, v−u) 算的，和 cross(u, v) 在最后几位不等； 只要一个采样点恰好落在两个三角形共享的边上、在一套算术里算"命中"、另一套算"未命中"， 这个像素的随机序列就整条错位 —— 它变成了另一个像素。

两种输出的"分辨力" 法线模式：像素 = f(n̂)，再量化到 8 bit  ⇒  10⁻¹⁶ 的差异被量化吸收 蒙特卡洛：像素 = f(几何 × 随机序列)  ⇒  噪声 σ ≈ 10/255，比几何差异大一个数量级

噪声比你要找的差异还大，逐像素比对就失去了分辨力。这时候"比对失败"不能说明几何错了 —— 更糟的是，"比对成功"也不能说明几何对了。一套对任何改动都报"相同"的实验，等于没有实验。

方法论
想验证几何，就要先把"随机"这个变量从实验里踢出去。
这和 Day 13 的"两步验收"是同一个思路：先关掉加速结构（变量：BVH），再关掉蒙特卡洛（变量：随机）。 图上一样不算数，字节一样才算数。

但"相同"也可能是方法太钝

这里要补一刀，否则"字节相同"毫无说服力：如果这个比对对任何改动都报相同，那它证明不了任何东西。所以今天顺手做了敏感性实验 —— 把立方体的一个顶点挪动 2%，看法线图会不会红。会红，说明这套比对有分辨力；在它有分辨力的前提下，"两种拆法字节相同"才是个结论。

bug 明明还在，为什么那 3 条能过？这一段是整份 devlog 里最值得反复读的。

Bug 是空 1 写错：把顶点当成了边向量。

两种写法 正确： Quad(a, b − a, c − a, mat) 错误： Quad(a, b, c, mat)

测试用的三角形恰好是 a=(1,0,0)、b=(1,1,0)、c=(0,1,0)。错误写法得到

恰好同向 u′ = b = (1,1,0),   v′ = c = (0,1,0) n′ = u′ × v′ = (0, 0, 1)   ←  和正确法线一模一样 所以平面没错（还是 z = 0），错的只是平面内的形状

因为 n′ = (0,0,1)，w′ = (0,0,1)，只有叉积的 z 分量有效 —— 那就是 2D 叉积：

错误的 α′、β′ α′ = px · v′y − py · v′x = px β′ = u′x · py − u′y · px = py − px 其中 p = P − a

把 7 个测试点代进去，结果和实测一字不差：

三绿四红。三个假绿的共同点：它们全都落在错误平行四边形与正确三角形的交集里。错误形状的角恰好是 a，而 a + v′ = b，所以 a 和 ab 中点都躺在它的边上。而重心 (2/3, 2/3) 在三角形的正中间，却在错误四边形的外面（α′ = −1/3 < 0）。

"假绿"说的不是"判错了"，而是"判对了也不能算数"：这三点确实在三角形里，PASS 本身没错；但它们不需要正确的参数化也能过，所以对定位 bug 的信息量是零。一条测试的价值 = 它能排除掉多少种错误，而不是它有多绿。

三条测试设计原则

① 顶点的"自身"永远最弱

顶点 a 无论 u、v 写成什么，只要 Q = a，它必然是 (0,0)，必然命中。测试点要挑"参数化之后才明确"的位置 —— 重心最好，因为它的 (α, β) = (1/3, 1/3)，错误的参数化几乎不可能凑出来。

② 两个形状的"差集"才有鉴别力，但只防一种错

"平行四边形第四角 (0,2,0)"这条，在 bug 版和正确版都判不命中，对这个 bug 完全无效。它防的是另一种错：把 is_interior 写成 return true;（退化成无限平面）。一条测试只防一种错。

③ 单点再准，也不如一整片网格

E 组打 7×7 = 49 条射线覆盖整个面，同时比 t 和法线。修复前 0/49，修复后 49/49。你不需要猜哪个点有鉴别力，因为整片都覆盖了。

细节 · 闭集与开集

09为什么内部判定用 >= 而不是 >

相邻两个三角形共享一条边。如果两边都用严格不等号，边界点会被同时拒绝。

这不是理论洁癖。在光栅化器里，屏幕坐标是定点数（比如 1/256 像素精度），大量采样点会精确落在边上。 如果两个三角形都把自己那条边判成"外面"，中间就出现一条谁都不画的黑缝 —— 也就是常说的三角形接缝闪烁。

工业界的标准解法是把"边界归谁"写成规则：top-left rule。左边界和上边界算内部，右边界和下边界算外部 —— 这样每个边界像素恰好被一个三角形认领，不重不漏。它比"全用开集"或"全用闭集"都精确，但需要知道三角形的绕向。

我们选更简单的一条：统一用闭集。

三角版 · 闭集 α ≥ 0  &&  β ≥ 0  &&  α + β ≤ 1
说实话
在路径追踪器里，这条缝几乎不可能出现。α、β 是浮点除法算出来的，正好等于 0 或 1 的概率是 0。 所以闭集在这套代码里更多是成本为零的正确性保险，不是修了什么实际 bug。 真正的战场在光栅化器里。

但选择闭集还有一个更深的理由，它和 Day 13 的 pad_to_minimums() 是同一个思维模式：

选错的代价闭集（可能重复命中）开集（可能漏命中）
后果极偶发的 z-fighting，绘制两次一条贯穿模型的黑线
肉眼看不出来一眼就看见
结论选它避开
当两种错误的代价不对称时，永远往代价小的那一侧倒。

自检题

为什么 Triangle 不需要重写 hit()？

因为 Quad::hit() 里调用的 is_interior(alpha, beta) 是 virtual 的。通过基类指针/引用调用虚函数时，实际执行的是对象真实类型的版本（多态）。所以同一份求交逻辑，配 Quad::is_interior 就是四边形，配 Triangle::is_interior 就是三角形 —— 行为由实际类型决定，不由代码位置决定。

三角形有 3 个顶点，为什么重心坐标只有 2 个数？

第三个权重是 1 − α − β，被"和为 1"这个约束隐含了。三个权重满足 w0+w1+w2=1，是 2 个自由度 —— 正好对应平面上的 2 个坐标。如果把三个权重都存下来，就会有一个冗余变量，且这个冗余会让"点在不在内部"的判据不稳定。

Triangle 的包围盒等于平行四边形的包围盒。会带来什么问题？不会带来什么？

会带来：BVH 叶子节点里多测一些"盒子相交但三角形不相交"的射线，效率略降（实测慢 53%，其中一半来自图元数翻倍）。
不会带来：任何正确性问题。包围盒只用于剪枝，偏大只意味着剪得不够狠，绝不会误伤命中。

如果 unit_vector((0,0,0)) 返回 NaN，为什么 if (fabs(denom) < 1e-8) 拦不住？

IEEE 754 规定任何涉及 NaN 的比较都返回 false（只有 != 返回 true）。所以 fabs(NaN) < 1e-8 → false，NaN <= t_min → false，NaN >= t_max → false。所有"把坏值挡在门外"的检查，遇到 NaN 会全部失效。唯一办法是在产生 NaN 之前拦住它 —— 这就是退化保护必须放在构造函数里的原因。

为什么 is_interior 用闭集（>= / <=）？

相邻三角形共享边，全用开区间会让边界点被两边同时拒绝，出现裂缝。但要说实话：在路径追踪器里 α、β 是浮点除法算出来的，恰好等于 0 或 1 的概率是 0，这条缝几乎不可能出现。真正的裂缝在光栅化器里（定点坐标 + 大量边界采样），那里的标准解法是 top-left rule。

选闭集的真正理由是代价不对称：重复命中 → 极偶发 z-fighting，肉眼看不出来；漏命中 → 一条贯穿模型的黑线，一眼就看见。

一个立方体用 6 个 Quad 还是 12 个 Triangle，哪个更快？

12 个 Triangle 更慢，实测 2.93 s → 4.48 s（200 spp）。两层原因：图元数翻倍（BVH 叶子候选从 18 涨到 36，每个面测两次）+ 包围盒更大（三角形的盒子是平行四边形的盒子，剪枝更松）。
但这是几十个图元的玩具场景。真实模型几十万三角形，"四边形省一半图元"的收益远比不上"三角形能表示任意形状"的能力。

四个可以亲手做的实验

  1. 注释掉退化保护，往场景里塞一个共线三角形。NaN 会污染整条光线路径 —— 可能是黑斑、条纹或者整片异色。
  2. 把 is_interior 改成严格不等号，渲染立方体。大概率看不出变化 —— 这正好说明"理论问题"和"实际问题"的区别。
  3. 把 --normal 下的立方体放大 4 倍，看每个面能不能看出对角线的分界。看不出，因为同一个面的两个三角形法线完全相同。想看见三角网格，必须按重心坐标着色或做顶点法线插值。
  4. 把退化判据改回 len2 < 1e-8，把立方体缩小到边长 0.01，看它会不会凭空消失。这是复现"epsilon 量纲错误"最快的办法。
