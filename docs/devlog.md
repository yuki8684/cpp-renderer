## Day 2 球体求交
- 球体方程：|P - C|² = r²
- 光线方程：P(t) = O + tD
- 代入展开：(D·D)t² + 2(OC·D)t + (OC·OC - r²) = 0 //o - c可以组合成向量OC，即球心指向相机的方向
- 判别式 Δ = b² - 4ac，其中 b = 2(OC·D)
  令 b′ = OC·D（半个 b），则 Δ = (2b′)² - 4ac = 4(b′² - ac)，判号只看 b′² - ac
  （求根时分母也从 2a 变成 a，详见下方「原理 1」）
  - Δ < 0：不相交
  - Δ = 0：相切
  - Δ > 0：两个交点
- 取较小的正 t
- 法线：N = (P - C) / r
- 法线着色：color = 0.5 * (N + 1)

## Day 2 · 三个核心原理（完整推导）

### 原理 1 · 球体求交：一次"代入 + 解方程"

**① 直觉**
问题：光线射出去，会不会碰到球？碰在哪儿？
关键转换：光线上的每个点都能用一个数 t 标出来（t 越大越远）。
于是问题变成 —— **"哪个 t 能让这个点正好落在球面上？"**

**② 两个方程，一个未知数**

- 光线：`P(t) = O + tD`   —— 点随 t 移动
- 球面：`|P - C|² = r²`   —— "点到球心的距离恰好等于半径"

把光线方程**代入**球面方程（把 P 换掉），就只剩 t 一个未知数：

    |O + tD - C|² = r²

**③ 展开**
令 `OC = O - C`（从球心指向相机起点的向量），则 `O + tD - C = OC + tD`：

    (OC + tD)·(OC + tD) = r²

用点积展开（利用 `|v|² = v·v`）：

    OC·OC + 2t(OC·D) + t²(D·D) = r²

整理成标准二次方程 `a·t² + b·t + c = 0` 的形式：

    a = D·D
    b = 2(OC·D)
    c = OC·OC - r²

**这就是"球体求交"的全部数学 —— 一个二次方程。**

**④ 判别式 `Δ = b² - 4ac` 的几何意义**

| Δ 的值 | 代数含义 | 几何含义 |
|---|---|---|
| Δ < 0 | 无实数解 | 光线从球旁边**掠过** |
| Δ = 0 | 一个重根 | 光线**擦边**（相切），恰好碰一个点 |
| Δ > 0 | 两个根 | 光线**穿过**球：先进后出 |

**⑤ 取哪个根？**

    t₁ = (-b′ - √Δ) / a        （较小的根）
    t₂ = (-b′ + √Δ) / a        （较大的根）

因为 `a = D·D > 0`，所以恒有 `t₁ ≤ t₂`。判断规则可以写得很紧：

- 若 t₁ 落在 `(t_min, t_max)` 内 → 它就是最近的 → **用它**
- 否则若 t₂ 在区间内 → **用它**（相机在球内时就是这种情况：t₁ < 0 < t₂）
- 两个都不在 → 判定为"没撞到"

⚠️ **只写"取较小的根"是错的**：相机位于球内部时 t₁ < 0，球会被渲染成一个黑洞。

### 原理 2 · 法线着色：把"朝向"变成颜色

**① 法线是什么**
球面上某点的**法线** = 该处曲面的垂直方向 = 从球心指向该点的方向：

    N = (P - C) / r

**为什么除以 r？** 球面上每一点都满足 `|P - C| = r`，所以 `(P - C) / r` 的长度恰好是 1。
除以 r 就顺便完成了归一化，比调用 `unit_vector()` 少一次开方。

**② 为什么法线能当颜色？**
观察：法线的三个分量各自落在 `[-1, 1]`，而颜色通道需要 `[0, 1]`。
两边都是"三个一组"的数 → **一个线性映射就能对上**：

    color = 0.5 × (N + 1)

| 法线方向 | 0.5 × (N + 1) | 看到的效果 |
|---|---|---|
| N = (+1, 0, 0) 面朝右 | (1.0, 0.5, 0.5) | 偏红 |
| N = (0, +1, 0) 面朝上 | (0.5, 1.0, 0.5) | 偏绿 |
| N = (0, 0, +1) 面朝相机 | (0.5, 0.5, 1.0) | 淡蓝白 |

**③ 它有什么用？**
这叫**法线可视化**，是渲染里最基础的调试手段：
- 画面"颜色不对"→ 一眼就能判断是不是法线方向错了
- 光滑与破面，在法线图上极其明显
- 后面做光照时法线是核心输入 —— 先用它上色，等于**先把法线单独验证一遍**

### 原理 3 · 多球体场景：怎么保证"看到的是最近的"

**① 问题**
场景里有 N 个物体，光线可能同时撞到好几个。屏幕上该显示哪个？
→ **最先撞到的那个**，也就是区间内 t 最小的那个。

**② 朴素做法**
对每个物体求交，收集所有合法 t，最后取最小。
逻辑正确，但**慢**：每个物体都得完整算一遍。

**③ 优化：让 t_max 当"当前最优成绩"**
把"已知的最近命中距离"记为 `closest`，初值取 `t_max`（还没找到命中时，上限就是无穷远）。
然后逐个物体问：

    对每个物体 obj：
        如果 obj 报告"我在 (t_min, closest) 内有交点 t"
            closest = t;      // 收紧上限
            提交 rec;

**关键在于传给物体的上界是 `closest`，而不是 `t_max`**：

- 第 1 个物体 → 在 `(t_min, ∞)` 内找
- 找到 `t = 3` → 后面的物体只在 `(t_min, 3)` 内找
- 更远的物体（t = 7）会被**自己的区间检查直接否掉**，连开方都可能省掉

**④ 为什么必须遍历完，不能提前 return？**
因为"第一个被遍历到的" ≠ "最近的" —— 物体在列表里的顺序和它们的远近毫无关系。
提前 return 会导致**近的球被远的球盖住**，这是最典型的 bug。

**⑤ 为什么用 `temp_rec`，而不是直接传 `rec`？**
**防御性设计**：`hit()` 未命中时返回 false，但如果某个实现"失败时也顺手改了 rec"，就会污染已找到的正确结果。
所以用临时报告单接住每次尝试，**只有真正命中时才提交**：

    rec = temp_rec;

### 架构：为什么要 Hittable 抽象（为什么非要绕这么大一圈）

> 这节回答一个很实际的问题：**直接写 `hit_sphere` 不行吗？为什么非要搞个抽象类？**

#### 第一步：先看"不抽象"会变成什么样

假设坚持用最简单的 `double hit_sphere(center, radius, ray)`。加第 1 个球很轻松：

```cpp
double t = hit_sphere(Point3(0, 0, -1), 0.5, r);
if (t > 0.0) { /* 上色 */ }
```

想加第 2 个球，就得自己写"选最近的"逻辑：

```cpp
double t1 = hit_sphere(Point3(0, 0, -1), 0.5, r);
double t2 = hit_sphere(Point3(1, 0, -1), 0.5, r);

double t;
if      (t1 > 0 && t2 > 0) t = std::min(t1, t2);   // 都撞到 → 取近的
else if (t1 > 0)           t = t1;
else if (t2 > 0)           t = t2;
else                       t = -1.0;               // 都没撞到
```

想加第 3 个球 → 上面那段要重写成三层嵌套。**那第 10 个球呢？**

再加个平面？还得写 `hit_plane()`，然后把这一整套比较逻辑**再抄一遍**。

#### 第二步：看清问题的本质

你每加一个物体，都在往 `main` 里堆"比较逻辑"。
但"**比较、找出最近的那个**"这件事，和"**物体长什么样**"完全无关 ——
球也好、平面也好，比较规则一模一样。**所以它不该写在 main 里。**

#### 第三步：解法 —— 让每个物体自己回答一个问题

> "光线 r，你在 (t_min, t_max) 区间内撞到了吗？撞到就把这张单子填好。"

- **球**会回答（解二次方程）
- **平面**会回答（解一次方程）
- **三角形**会回答（后面会学 Möller–Trumbore 算法）
- **`HittableList` 自己也会回答**（挨个问所有物体，保留最近的那份）

于是 `main` 里那段丑陋的 if-else **整个消失了**，只剩两行：

```cpp
if (world.hit(r, 0.0, infinity, rec)) { /* 上色 */ }
```

**不管世界里有 1 个球还是 100 万个三角形，这两行都不用改。**

#### 第四步：这就是"多态"

为了能"统一地问"，所有物体必须先约定**同一个函数签名** —— 这就是 `Hittable`：

```cpp
class Hittable {
public:
    virtual bool hit(const Ray&, double, double, HitRecord&) const = 0;
};
```

- `virtual` = "这个函数**具体怎么做**由子类决定，调用时你自动去找对的那个"
- `= 0` = "我没有默认实现，**任何继承我的类都必须自己实现**"

所以 `Sphere` 继承它，`HittableList` 也继承它。
而 `HittableList` 里存的是 `Hittable` 指针 —— **它完全不知道装的是球还是别的**，
调 `hit()` 时 C++ 自动派发到正确的实现。

#### 今晚的回报（一算就知道）

- 加"两个球 + 一个地面"：只改了 `main.cpp` 里两行 `world.add(...)`
- 如果没抽象：得改三处比较逻辑，而且每加一个物体都要再改一次

> 💡 **面试常问**："你的渲染器怎么支持多种物体？"
> 答案就是这个 —— 抽象基类 + 虚函数。
> 它不是为了"架构好看"，是为了**避免写出指数级膨胀的 if-else**。

### t_min / t_max 的作用（今天最重要的理解）
- `t_max`：把"已找到的最近距离 closest"传给下一个物体，更远的命中被自动排除
  → 既保证遮挡正确，又省下大量求交计算
- `t_min`：小正数（如 0.001），防止光线打到"自己刚离开的那个表面"（shadow acne）
  现在传 `0.0`，做阴影 / 反射时才会用到
- `HittableList::hit` 必须**遍历完整个列表**；提前 return 会拿到"最后一个"而不是"最近的"

### 半 b 优化（Day 2 自检题 Q2 的答案）
由 Δ = b² − 4ac，令 **b′ = OC·D**（半个 b），则：

    Δ = (2b′)² − 4ac = 4(b′² − ac)          → 判号等价于 b′² − ac
    t = (−b′ ± √(b′² − ac)) / a             → 分母的 2a 也变成了 a

⚠️ 变量名必须叫 `half_b` / `b_prime`，**绝不能叫 b**，否则极易误写成 `b*b - 4*a*c`


### 验证方式：用几何反推（怎么判断"渲染对不对"）

> 这节回答：**图渲染出来了，我凭什么说它是对的？**

#### 为什么"看起来对"不算数

渲染器最讨厌的 bug 不是"全黑"或"崩溃"（那些一眼能看出来），
而是"**位置差一点点**"、"**遮挡偶尔反了**" —— 肉眼几乎发现不了，但说明数学里有错。

**正确做法**：先用数学算出"**理论上它应该在哪儿**"，再去图上量"**实际在哪儿**"，两边对上了才算通过。

#### 先备好两件工具（只用到这一次，不用怕三角函数）

算"球在画面上占多大"要用一点点三角，其实只有两步：

1. **求"看起来有多宽"的角度**
   画个直角三角形（相机 → 球心 → 球面切点）。切点处半径 ⊥ 视线，所以

       sin θ = r / d        （半径 ÷ 相机到球心的距离）

2. **把角度换算到屏幕上**

       横向偏移 = tan θ      （读作"往前 1 个单位，横向偏多少"）

用计算器算两个数就够：`asin(0.5) = 30°`、`tan(30°) = 0.577`。

#### 检查 1（最简单）：球是不是正好坐在地面上？

- 球心 y = 0，半径 0.5          →  **球底** y = -0.5
- 地面球心 y = -100.5，半径 100  →  **顶面** y = -100.5 + 100 = -0.5

两者相等 → 球应该**正好贴着**地面：不悬空、也不陷进去。✅ 对上了。
（如果悬空或陷入 → 说明某个球心坐标或半径写错了）

#### 检查 2：左球居中吗？占多宽？

- **位置**：球心 (0, 0, -1)，方向正好是 -z  →  画面水平正中，`u = 0.5`  ✅
- **宽度**：d = 1，r = 0.5  →  sin θ = 0.5  →  θ = 30°  →  tan 30° = 0.577
  - 横向：`u = 0.5 ± 0.577 / 3.556 = 0.5 ± 0.162`  →  **u ∈ [0.34, 0.66]**（约占 1/3 宽）✅
  - 纵向：`v = 0.5 ± 0.577 / 2.0   = 0.5 ± 0.289`  →  **v ∈ [0.21, 0.79]**
    （实测左球顶端在 v = 0.786，理论 0.789 —— 差不到 1 个像素 ✅）

#### 检查 3（最能说明问题）：右球应该被画面右边裁掉一截

- d = √2 ≈ 1.414，r = 0.5   →   sin θ = 0.354   →   θ ≈ 20.7°
- 球心方向偏 45°（因为 x = 1 和 z = -1 等长）
- 右边界角度 = 45° + 20.7° = 65.7°   →   tan 65.7° ≈ 2.21
  →   u = 0.5 + 2.21 / 3.556 = **1.12**

**1.12 已经超出画面（u 最大到 1）** → 右球右侧有一截在画面外。✅ 看图：确实被右边缘切掉。

#### 检查 4：遮挡关系

左球球心距相机 1.0，右球 √2 ≈ 1.414 → **左球更近** → 左球应该压在右球上面。✅ 对上了。

> ⚠️ 这一条是 `t_max` 逻辑正确与否的**最强证据**。
> 如果传给物体的上界写成 `t_max` 而不是 `closest`，右球会反过来盖住左球。

### 原理 1 · 抗锯齿（Antialiasing）

#### 1.1 为什么会有锯齿

原来每个像素只射**一条**光线。这条光线要么撞到球、要么没撞到 —— **没有中间状态**。
所以球和天空的交界处只能"一刀切"，看起来是楼梯状。

但现实里一个像素覆盖的是**一小块面积**。如果这块面积**一半是球、一半是天空**，
正确的颜色应该是**两者的混合**。

#### 1.2 解法：一个像素射 N 条光线，取平均

手算例子（N = 4）：

    3 条撞到球   → 球是白色 (1.0, 1.0, 1.0)
    1 条撞到天空 → 天空是 (0.5, 0.7, 1.0)

    color = (3 × (1.0, 1.0, 1.0) + 1 × (0.5, 0.7, 1.0)) / 4
          = (3.5, 3.7, 4.0) / 4
          = (0.875, 0.925, 1.0)

这个像素就变成了"淡蓝白" —— 介于球和天空之间的颜色，边缘就"软"了。

**核心只有两步：累积（`+=`）→ 除以样本数。**

#### 1.3 三层循环的结构（重要）

    for (int j = 图像高度-1; j >= 0; --j)          ← 第 1 层：逐行
        for (int i = 0; i < 图像宽度; ++i)          ← 第 2 层：逐列（这两层 = 走到一个像素）
            Color pixel_color(0,0,0);              ← 这个像素的累积器（必须在这层）
            for (int s = 0; s < samples_per_pixel; ++s)     ← 第 3 层：采样
                u = (i + random_double()) / image_width     ← 在像素【内部】随机取点
                v = (j + random_double()) / image_height
                Ray r = camera.get_ray(u, v);
                pixel_color += ray_color(r, world);
            Color color = pixel_color / samples_per_pixel;   ← 平均
            写这个像素的 RGB

**层级自检表** —— 问自己"这行代码是**每个像素**执行一次，还是**每行**一次？"

| 语句 | 该在哪一层 | 理由 |
|---|---|---|
| samples_per_pixel | main 开头（循环外） | 全图共用一个值 |
| 进度提示 | for j 里 | 每行一次 |
| pixel_color | for i 里、for s 外 | 每个像素一个累积器 |
| u / v / Ray r | for s 里 | 每次采样都要重新随机 |
| 写像素的 RGB | for i 里 | 每个像素写一组 |

#### 1.4 追问 1：为什么用"随机"，而不是固定在 4 个角采样？

固定规则采样会在重复图案上产生**规则的干涉纹**（摩尔纹）—— 会出现本不存在的花纹。

随机采样产生的是**噪声**：看起来像颗粒，但它是均匀的，采得越多越干净，**不会产生假图案**。

这个思想叫**蒙特卡洛方法**。后面做景深、软阴影、全局光照全靠它。

#### 1.5 追问 2：采样数的代价律 —— 1/√N

**结论：采样数 × N → 噪声 ÷ √N。**

推导（两步）：

    第 1 步：N 个独立误差【相加】，波动涨的不是 N 倍，而是 √N 倍
            （因为正负误差互相抵消了一部分）
                和值的波动 = σ · √N

    第 2 步：再除以 N 取平均
                平均值的波动 = σ · √N / N = σ / √N

（σ 是希腊字母 sigma，表示"单个采样的波动大小"。）

**这张表决定了"抗锯齿有多贵"：**

| 采样数 | 相对时间 | 相对噪声 |
|---|---|---|
| 4 | 1× | 1.00 |
| 16 | 4× | 0.50 |
| 64 | 16× | 0.25 |
| 400 | 100× | 0.10 |

**时间涨 4 倍，噪声只降一半。想要干净 10 倍，成本 100 倍。**

这也是为什么工业界要发明更好的采样方法（分层采样 / 蓝噪声 / 降噪器）。

#### 1.6 追问 3：为什么除以 image_width，而不是 (image_width - 1)？

    (i + 随机) / (W - 1)   →   i = W-1 时 u ∈ [1, 1.009)   ✗ 超出视口
    (i + 随机) / W         →   u ∈ [0, 1)                 ✓ 永远不越界

深层理解：

- 除以 (W-1) 是"把像素当成一个**点**"的写法（Day 1 的遗留）
- 除以 W 才是"把像素当成一段**区间**"—— 抗锯齿的核心就是承认像素有面积

顺带：像素 i 覆盖的范围是 [i/W, (i+1)/W)，中心在 (i+0.5)/W。

### 原理 2 · 漫反射材质（Diffuse / Lambertian）

#### 2.1 从"光线停住"到"光线弹射"

**旧模型**：光线 → 撞到球 → 结束，返回法线颜色（这是假的，不是任何真实材质）

**新模型**：光线 → 撞到球 → 朝随机方向再射一条 → 又撞到东西 → 再射…
最后射向天空 → 返回天空色，然后**逐层打折**返回。

**这才是"光线追踪"里"追踪"二字的真正含义。**

哑光表面（石膏、粉笔、纸、未上漆的木头）的特征：光线打上去**朝四面八方散射**，
所以你从任何角度看颜色都差不多。

#### 2.2 手算：一条光线的一生

    第 1 步  相机光线撞到球
    第 2 步  弹射出一条新光线
    第 3 步  新光线射向天空 → 天空色 = (0.5, 0.7, 1.0)
    第 4 步  往回衰减：0.5 × (0.5, 0.7, 1.0) = (0.25, 0.35, 0.5)
    第 5 步  这个颜色就是那个像素的颜色

**结论（很重要）：漫反射球的颜色 = 打折的环境色。**

球本身**没有颜色**，它只是"把照到它身上的光原样反射，再打 5 折"。
而照到球上的光全部来自那片蓝天 → 所以球是"暗掉的蓝天色"。

#### 2.3 怎么选"随机方向"（今天最难的一点）

**两个要求：**

1. 要**随机**（不能每次方向都一样，否则不是漫反射）
2. 必须朝**外**（射进球体内部的话，渲染结果完全错）

**解法：方向 = 法线 N + 随机单位向量 s**

先把 N 固定，看 s 取各种值时的结果（设 N = (0, 1, 0)）：

| 随机取到的 s | N + s | 方向 | 会射进球里吗 |
|---|---|---|---|
| (0, 1, 0) 正上 | (0, 2, 0) | 正上方 | 不会 |
| (1, 0, 0) 正右 | (1, 1, 0) | 右上 45° | 不会 |
| (0, 0, 1) 正前 | (0, 1, 1) | 前上 45° | 不会 |
| (0, -0.707, 0.707) 斜下 | (0, 0.293, 0.707) | 还是朝上偏前 | 不会 |
| (0, -1, 0) 正下 | (0, 0, 0) | 零向量（退化情形） | 不会（只是贴着表面） |

**一个都射不进去。**

**证明** —— 盯住"沿法线方向的分量"：

    (N + s) · N  =  N·N + s·N  =  1 + (s·N)

因为 s 是单位向量，s·N 的范围是 [-1, 1]，
所以 1 + (s·N) 的范围是 **[0, 2]，永远 ≥ 0**。

点积 ≥ 0 ⇔ 夹角 ≤ 90° ⇔ 方向一定在外半球。∎

**几何图像：**

    在交点外侧、"贴着"表面放一个半径 1 的小球
    （球心在「交点 + N」，与表面只在交点处相切，其余部分全在表面外侧）

    在这个小球面上随便取一个点 s，
    那么从交点指向那个点的方向，必然朝外。

**为什么不能"直接用 s 当方向"？**
s 可能指向正下方 → 射进球体内部 → 光线从球里面又撞到球面 → 画面出现黑斑 / 内部发光。
所以必须 **+ N**，把方向"拉"到外侧。

#### 2.4 代码（三行）

    Vec3 s        = random_unit_vector();     // 随便指哪都行，长度 1
    Vec3 target   = rec.p + rec.normal + s;   // 目标点 = 交点 + 法线 + s，target是一个Vec3的点
    Ray  scattered(rec.p, target - rec.p);    // 起点 = 交点，方向 = 指向目标

    return 0.5 * ray_color(scattered, world); // 递归 + 衰减

展开 `target - rec.p = (rec.p + rec.normal + s) - rec.p = rec.normal + s` —— 就是 N + s。
`target` 只是"用点的形式表达方向"，写成 `Ray(rec.p, rec.normal + s)` 效果完全一样。

#### 2.5 怎么在单位球面上取随机点（拒绝采样）

    while (true) {
        Vec3 p(random_double(-1,1), random_double(-1,1), random_double(-1,1));
        double len2 = p.length_squared(); //原点到点的距离,p的模的平方
        if (len2 > 1.0 || len2 < 1e-8) continue;   // 球外 / 太靠近原点 → 重取
        return unit_vector(p);
    }

- `len2 > 1.0` → 落在立方体的角上（球外），拒绝
- `len2 < 1e-8` → 太接近原点，归一化会除以接近 0 的数 → NaN，拒绝

立方体体积 8，球体积 4π/3 ≈ 4.19，**命中率约 52%** —— 平均取两次成功一次，可以接受。

**这叫"拒绝采样"**：想生成 A 分布的样本、但只会生成 B 分布时的通用招数。

#### 2.6 追问 1：为什么 t_min 必须是正的小数？

**这就是 Day 2 埋下的伏笔 —— shadow acne（阴影痤疮）。**

弹射光线的**起点就是交点本身**。由于浮点误差，起点可能落在表面**里面一点点**，
于是它立刻"撞到自己"、返回黑色 → 画面出现**满屏斑点**。

把 t_min 设成一个小正数（本项目用 0.01），就强制"忽略距离 0.01 以内的交点"，把起点推离表面。

#### 2.7 追问 2：递归会不会无限进行下去？

**理论上会。** 实际上每次衰减 0.5，颜色很快趋近 0，贡献可忽略。
但**生产环境必须限制**：加一个 depth 参数，超过就返回黑色。（RTIOW 没加，这是个小坑。）

递归必须有两样东西：

1. **终止条件**（否则无限递归 → 栈溢出崩溃）
2. **每次递归向终止条件靠近**

在 `ray_color` 里：终止条件 = "没撞到任何东西 → 返回背景色"。

### 今天的架构变化：`ray_color` 被提取成独立函数

原来"光线 → 颜色"的逻辑写在像素循环里。今天把它搬出来：

    Color ray_color(const Ray& r, const Hittable& world);

**为什么必须搬出来？**
因为漫反射需要**递归** —— `ray_color` 调用自己。写在像素循环里根本没法递归。

**它的契约极干净**：输入"一条光线 + 一个世界"，输出"一个颜色"，无副作用。
正因为干净，它才能自己调用自己。

### C++ 技能点（今天新学）

#### 1. 作用域（Scope）
变量从**声明那一刻**起，到它所在的**那一层 `}`** 为止才存在。

    int main() {
        int a = 1;          // a 在整个 main 里活着
        {
            int b = 2;      // b 只在这个 {} 内活着
            a = 5;          // ✅ 内层可以改外层
        }
        b = 3;              // ❌ 错：b 已经死了
    }

三条推论：
- 内层看得见外层，外层看不见内层
- 离开 `{}` 变量就销毁（所以 pixel_color 必须放在采样循环**外面**，否则每次采样都清零）
- **内层同名变量会"遮蔽"外层** —— 编译器不报错，只是行为不对，最阴险

#### 2. 函数不能嵌套

    int main() {
        int f() { return 1; }    // ❌ C++ 不允许
        // 报错：a function-definition is not allowed here
    }

    int f() { return 1; }        // ✅ 定义在文件作用域（main 外面）

#### 3. 函数重载（Overloading）
两个同名函数，靠**参数个数 / 类型**区分：

    inline double random_double()                          // [0, 1)
    inline double random_double(double min, double max)    // [min, max)

编译器根据你传几个参数自动选。这不是"重复定义"，是合法的。

#### 4. 递归（Recursion）
函数调用自己。必须有两样东西：终止条件 + 每次向终止条件靠近。

#### 5. 局部 static 变量

    inline double random_double() {
        static std::uniform_real_distribution<double> distribution(0.0, 1.0);
        static std::mt19937 generator;
        return distribution(generator);
    }

函数内的 `static` 变量**只初始化一次**，之后每次调用复用同一个对象。
这里很关键：如果每次都新建 generator，它会被重新播种，随机性会**退化**。

#### 6. 声明顺序（C++ 是单遍扫描的语言）
函数用到的类型和函数，必须在它**之前**已经"见过"。
所以 `random_unit_vector()` 返回 `Vec3`，就不能写在 `rtweekend.h`（那里没有 Vec3），
必须写在 `vec3.h` 末尾，同时 `vec3.h` 顶部 `#include "rtweekend.h"`。

### 原理 1 · 材质接口：`scatter()` 的契约

```cpp
class Material {
public:
    virtual ~Material() = default;
    virtual bool scatter(const Ray& r_in, const HitRecord& rec,
                         Color& attenuation, Ray& scattered) const = 0;
};
```

其实就是一句话：

> **"光线打在你身上，会往哪儿弹？回来的时候打几折？"**

| 参数 | 方向 | 含义 |
|---|---|---|
| `r_in` | 输入 | 射进来的光线 |
| `rec` | 输入 | 命中信息（交点、法线、front_face） |
| `attenuation` | **输出** | 反射率（打几折，是个颜色） |
| `scattered` | **输出** | 弹射出去的光线 |

返回 `bool` = "这次有没有发生散射"（返回 false 表示光被吸收）。

**规律**：`const T&` 是输入，`T&` 是输出。这个规律在 C++ 里很通用。

#### ⭐ 为什么 `attenuation` 是 `Color` 而不是 `double`？

**因为材质可以有颜色。** "物体的颜色"在物理上就是"它对各色光的反射率"：

| albedo | 效果 |
|---|---|
| (1, 1, 1) | 全反射 → 白 |
| (0.5, 0.5, 0.5) | 反射一半 → 灰 |
| (0.9, 0.3, 0.3) | 只反射红光 → 红 |
| (0.2, 0.4, 0.9) | 蓝通道占优 → 蓝 |

**这就是"有颜色的球"的实现方式** —— 不是给球涂色，而是改变它反射光的比例。

#### 一个类比：为什么"抽象"比"写死"好

**写死的版本**相当于：

    老板说："每个人的工资都是 5000。"
    来了个新员工要 8000 → 修改全公司的工资规则 → 所有人都受影响

**抽象的版本**相当于：

    老板说："每个人自己报工资。"
    你来应聘 → 你报你的；我来应聘 → 我报我的

`Material` 就是那句"每个人自己报工资" —— 它只规定**接口**（你必须能回答"往哪弹、打几折"），
不规定**具体数值**。所以 `Lambertian` / `Metal` / `Dielectric` 可以各报各的。

而 `ray_color` 就是那个"老板" —— **它不需要知道任何具体数字，只负责收答案。**

#### ⚡ 能量守恒：为什么 `attenuation` 每个通道都必须 ≤ 1

这是个**物理约束**，不是代码规范：

    入射光的能量 = 反射的光 + 吸收的光 + 透射的光

所以**反射出去的比例不可能超过 1**。

**如果谁写出 `attenuation = (1.2, 1.2, 1.2)` 会怎样？**

    第 1 次弹射：颜色 × 1.2
    第 2 次弹射：颜色 × 1.44
    第 3 次弹射：颜色 × 1.728
    ...
    第 50 次弹射：颜色 × 9100      ← 递归下去会指数爆炸

结果：画面**大面积全白**（过曝），而且**违背物理**。

> **物理上"反射率 > 1"的物体是不存在的** —— 那就成了"发光体"（自发光/荧光），
> 那是另一类材质（`Emissive`），需要**额外的光源项**，不能用这种"乘衰减"的模型。

**顺带解释了几件事：**

| 材质 | attenuation | 为什么 |
|---|---|---|
| Lambertian | albedo，通常 ≤ 0.9 | 真实哑光表面会吸收一部分光 |
| Metal | albedo，通常 ≤ 1 | 抛光金属接近全反射（银 ≈ 0.97） |
| **Dielectric** | **(1, 1, 1)** | **理想化的"完全不吸光"** —— 真实玻璃会吸收一点点（普通玻璃因含铁，对绿光吸收最少，边缘看会偏绿） |
| 自发光体 | > 1 的概念 | **这个模型装不下**，需要单独的"发光"接口 |

**这也是为什么前面说"纯 (1,0,0) 的红球看起来假"** ——
它意味着红通道 100% 反射、绿蓝通道 0% 反射，自然界不存在这种极端值。

### 原理 2 · `ray_color` 变成"问材质"

```cpp
Color ray_color(const Ray& r, const Hittable& world, int depth) {
    if (depth <= 0) return Color(0, 0, 0);        // 保险丝，见原理 5

    HitRecord rec;
    if (world.hit(r, 0.01, infinity, rec)) {
        Ray   scattered;
        Color attenuation;

        if (rec.mat->scatter(r, rec, attenuation, scattered))     // 问材质
            return attenuation * ray_color(scattered, world, depth - 1);
        return Color(0, 0, 0);                    // 材质把光吸收了
    }

    // 天空渐变（不变）
    Vec3 unit_dir = unit_vector(r.direction());
    double t = 0.5 * (unit_dir.y() + 1.0);
    return (1.0 - t) * Color(1.0, 1.0, 1.0) + t * Color(0.5, 0.7, 1.0);
}
```

**关键那一行**：

    attenuation * ray_color(scattered, world, depth - 1)

`attenuation`（反射率）和"弹射后带回来的颜色"**逐元素相乘**，就是"这条弹射光贡献了多少颜色"。

> ⚠️ 这是 `Vec3 × Vec3`（**逐元素乘**），不是标量乘。
> albedo = (1, 0, 0) 时，绿蓝通道直接归零 → 纯红。

**`ray_color` 从此完全不知道"哑光""金属"这些词。** 加新材质不用改它一个字。

#### 2.1 一条光线走完全程（数值追踪）

光看公式容易飘，跟着一条光线走一遍就清楚了。

**场景**：红哑光球 `albedo = (0.9, 0.3, 0.3)`，天空色记作约 `(0.7, 0.8, 1.0)`。

**最简单的情况 —— 一次弹射：**

    相机射出一条光线
      ↓ 撞到红球 → scatter() 返回 attenuation = (0.9, 0.3, 0.3)，弹射方向朝上
      ↓ 递归 ray_color(scattered, world, depth−1)
          ↓ 这条新光线射向天空
          返回 天空色 (0.7, 0.8, 1.0)
      ↓ 回到上一层
      返回 (0.9, 0.3, 0.3) × (0.7, 0.8, 1.0)

**逐通道乘开：**

| 通道 | 计算 | 结果 |
|---|---|---|
| 红 | 0.9 × 0.7 | 0.63 |
| 绿 | 0.3 × 0.8 | 0.24 |
| 蓝 | 0.3 × 1.0 | 0.30 |

得到 `(0.63, 0.24, 0.30)` —— 一个**暗红**。正是红球该有的颜色。

---

**复杂一点 —— 三次弹射：**

    相机光线 → 红球 → 弹射
                    ↓
                 地面 (albedo 0.8, 0.8, 0.0) → 弹射
                    ↓
                 红球 → 弹射
                    ↓
                 天空 (0.7, 0.8, 1.0)

**从天空往回乘：**

| 步骤 | 颜色 | 发生了什么 |
|---|---|---|
| 起点（天空） | (0.70, 0.80, 1.00) | — |
| × 红球 | (0.63, 0.24, 0.30) | 被红球**滤了一次**：绿蓝被压到 0.3 倍 |
| × 地面 | (0.504, 0.192, 0.00) | 被地面**滤掉了全部蓝光**（地面 albedo 蓝通道 = 0） |
| × 红球 | (0.4536, 0.0576, 0.00) | 又滤一次红，绿蓝再 ×0.3 |

最终 `(0.45, 0.06, 0.00)` —— 一个**很暗的红**。

**这条光线的大半能量，被红球吸收了两次、被地面滤掉了整个蓝色通道。**

> ⭐ **这就是"颜色相乘"的物理含义：**
> **每一次弹射都是一次"滤色"。** 物体把"自己不反射的波长"吸收掉，
> 剩下的才继续往下传。乘了几次，颜色就被"筛"了几次。
>
> 这也解释了为什么**间接光是"脏"的** —— 弹射越多次的光，被滤得越厉害，
> 颜色越偏离原始光源的颜色。

### 原理 3 · Lambertian（哑光）

```cpp
bool scatter(...) const override {
    Vec3 direction = rec.normal + random_unit_vector();   // ① 随机方向（保证在外半球）
    scattered      = Ray(rec.p, direction);               // ② 起点=交点
    attenuation    = albedo;                              // ③ 反射率
    return true;
}
```

#### 为什么 `rec.normal + random_unit_vector()` 一定指向【球外】？

`random_unit_vector()` 返回的是"随便指哪都行"的单位向量 —— 它**可能指向球体内部**。
所以必须加一个 `rec.normal` 把它"拉"到外侧。证明如下。

**先把法线方向固定下来看**。设 `N = (0, 1, 0)`（朝上），随机向量记作 `s`（单位长度）。
那么 `s` 的 y 分量必然落在 `[−1, 1]` 之间。于是：

    (N + s) 的 y 分量 = 1 + (s 的 y 分量) ∈ [0, 2]

**永远 ≥ 0。** 也就是说：**无论 `s` 怎么随机，结果永远朝上（朝外）。**

**一般化写（不依赖具体坐标）**：

    (N + s) · N  =  N·N + s·N  =  1 + (s·N)  ≥  1 − 1  =  0

**点积 ≥ 0 ⇔ 夹角 ≤ 90° ⇔ 方向在外半球。** ∎

**逐个情况验证**（设 N = (0,1,0)）：

| 随机取到的 s | N + s | 指向 | 会射进球里吗 |
|---|---|---|---|
| (0, 1, 0) 正上 | (0, 2, 0) | 正上方 | 不会 |
| (1, 0, 0) 正右 | (1, 1, 0) | 右上 45° | 不会 |
| (0, 0, 1) 正前 | (0, 1, 1) | 前上 45° | 不会 |
| (0, −0.707, 0.707) 斜下 | (0, 0.293, 0.707) | 还是朝上偏前 | 不会 |
| (0, −1, 0) 正下 | (0, 0, 0) | 零向量（退化情形） | 不会（只是贴着表面） |

**一个都不射进球里。**

**几何图像**：在交点外侧、"贴着"表面放一个半径 1 的小球
（球心在「交点 + N」，与表面只在交点处相切，其余部分全在表面外侧）。
在这个小球面上随便取点 `s`，从交点指向那个点的方向，**必然朝外**。

**⚠️ 一个不精确的地方（现在是"可接受的近似"）**：
`N + s` 在半球内的分布**不是均匀的** —— 它偏向法线方向。
真正严格的 Lambertian 需要按 `cos θ` 加权。
RTIOW 用的就是 `N + s` 这个简化版，视觉上已经足够像漫反射。
（想严谨的话，后面可以改成 `N + random_unit_vector()` 再乘一个 cos 权重。）

**`r_in` 参数用不上** —— 因为哑光散射的方向**和入射方向无关**（不管光从哪边来，都是随机弹）。
编译器会警告 `unused parameter 'r_in'`，这是**设计如此**，不是 bug。

#### 为什么真实物体的 albedo 很少是 1 或 0？

| 物体 | albedo |
|---|---|
| 白纸 | ≈ 0.8 |
| 雪 | ≈ 0.9 |
| 黑天鹅绒 | ≈ 0.01 |

**"纯 0"和"纯 1"是自然界不存在的极端值** —— 这也是为什么 `albedo=(1,0,0)` 的球看起来"假"。

### 原理 4 · Metal（金属）

#### 4.1 反射公式 `d − 2(d·n)n` 的完整推导

**第 1 层 · 直觉**：打台球撞库边 —— **垂直于库边的分量反向，平行于库边的分量不变**。

**第 2 层 · 手算一个例子**
设入射方向 `d = (1, −1, 0)`，法线 `n = (0, 1, 0)`：

    拆： d = (1, 0, 0)  +  (0, −1, 0)
            ↑ 切向           ↑ 法向
    反射： 切向不变       法向翻转
           (1, 0, 0)      (0, +1, 0)
    合起来：(1, 1, 0)
    进 (1,−1,0) 出 (1,1,0) —— 完美对称 ✓

**第 3 层 · 怎么用 d 和 n 算出这两个分量**

    d·n = d 在 n 方向上的投影长度（带符号）
    法向分量 = (d·n) · n
    切向分量 = d − (d·n) · n
        （验证：切向分量 · n = 0，确实垂直于 n）

**第 4 层 · 合成，"2" 的来历**

    反射 = 切向 − 法向
         = [d − (d·n)n] − (d·n)n
         = d − 2(d·n)n

    第 1 次 − (d·n)n：把法向分量【扣掉】→ 得到切向
    第 2 次 − (d·n)n：把法向分量【反向加回】
    总共减了两次 → 系数 2

**第 5 层 · 三个验证**

| 入射 d | n | d·n | 反射 |
|---|---|---|---|
| (0, −1, 0) 垂直 | (0,1,0) | −1 | (0, 1, 0) 垂直弹回 ✓ |
| (0.7071, −0.7071, 0) 45° | (0,1,0) | −0.7071 | (0.7071, 0.7071, 0) ✓ |
| (0.99, −0.141, 0) 近平行 | (0,1,0) | −0.141 | (0.99, 0.141, 0) ✓ |

**⚠️ 符号约定**：`v` 必须指向表面**内部**（光线前进的方向）。
在代码里 `r_in.direction()` 天然满足。**验证：这时 `d·n < 0`。**
如果哪天反射方向整个反了，第一个检查这个。

#### 4.2 代码

```cpp
inline Vec3 reflect(const Vec3& v, const Vec3& n) {
    return v - 2 * dot(v, n) * n;
}

bool Metal::scatter(...) const override {
    Vec3 reflected = reflect(unit_vector(r_in.direction()), rec.normal);
    scattered   = Ray(rec.p, reflected + fuzz * random_unit_vector());
    attenuation = albedo;
    return dot(scattered.direction(), rec.normal) > 0;
}
```

#### 4.3 追问

**Q1：为什么反射前要 `unit_vector`？**

先说**公式本身**：`v − 2(v·n)n` 对**任意长度**的 v 都成立。因为

    |v − 2(v·n)n|² = |v|² − 4(v·n)² + 4(v·n)²|n|² = |v|²         （|n| = 1 时）

**长度保持不变**，方向也正确。所以从"求反射方向"这个目的来说，不归一化也行。

**但 fuzz 需要归一化。** 因为 `fuzz × random_unit_vector()` 是"在**单位球**内扰动"：

    fuzz = 0.1、reflected 长度为 1    → 扰动幅度是反射向量的 10%
    fuzz = 0.1、reflected 长度为 5    → 扰动幅度只有反射向量的 2%

**扰动的相对大小会随长度变化** —— 那就没法用一个统一的 `fuzz` 参数控制粗糙度了。

**归一化之后，`fuzz = 0.1` 永远是"扰动 10%"，和场景尺度无关。**

**Q1-补充：`fuzz` 在物理上对应什么？**

真实金属表面在**微观**上不是平的，而是由无数微小的"镜面小片"（microfacet）组成。
每个小片都完美反射，但**朝向**略有不同。宏观上看起来就是"糊掉的反射"。

`fuzz` 就是对这个现象最粗暴的模拟：**不建几何，直接在反射方向上随机抖一下。**
（真实的 PBR 用"粗糙度 roughness + 法线分布函数 D(θ)"来建模，更精确 —— 那是后面阶段二的事。）

**Q2：为什么 `fuzz` 要在构造函数里夹到 ≤ 1？**
`fuzz > 1` 时扰动半径比反射向量本身还大 → 方向可能被推到完全相反的方向 → 诡异光斑。

    Metal(const Color& albedo, double fuzz)
        : albedo(albedo), fuzz(fuzz < 1 ? fuzz : 1) {}

这叫**防御性编程**：不管外面传什么鬼值，对象内部始终合法。

**Q3：`return dot(...) > 0;` 是什么意思？**
fuzz 扰动可能把方向推到**表面下面**（射进金属内部）。金属不透明，那种光线不该存在。
- 朝外（`dot > 0`）→ true，正常散射
- 朝里（`dot < 0`）→ false，被吸收（`ray_color` 返回黑色）

> 💡 `fuzz = 0.0` 时 `reflected` 永远朝外，**这一行不写也看不出问题**。
> 但 `fuzz = 0.3` 时就会冒出黑点。**这是一个"测试才能发现"的 bug。**

### 原理 5 · Dielectric（玻璃 / 水 / 钻石）

#### 5.1 直觉：三种情况

    情况 A：空气 → 玻璃    折射后【偏向】法线
    情况 B：玻璃 → 空气    折射后【偏离】法线
    情况 C：角度太大       出不去，全部弹回 ← 全反射（光纤原理）

**折射率 η（eta）**：空气 1.0 | 水 1.33 | 玻璃 1.5 | 钻石 2.42

#### 5.2 Snell 定律与全反射判据

    η₁ · sin θ₁ = η₂ · sin θ₂

换成更有用的形式：

    sin θ₂ = (η₁ / η₂) · sin θ₁ = eta_ratio · sin θ₁

**⚡ 全反射判据**：`sin` 不可能大于 1。所以

    如果 eta_ratio · sin θ₁ > 1   →   折射在物理上不可能 → 全部反射回去

**eta_ratio 是哪个除以哪个**：

| 光怎么走 | eta_ratio |
|---|---|
| 空气 → 玻璃 | 1.0 / 1.5 ≈ 0.667 |
| 玻璃 → 空气 | 1.5 / 1.0 = 1.5 |

**两种情况互为倒数。** 所以程序必须知道"这次碰撞是从外面还是从里面"。

**顺带解释了"全反射主要发生在玻璃→空气方向"**：
玻璃→空气时 eta_ratio = 1.5 > 1，`1.5 × sin θ₁` 很容易超过 1；
空气→玻璃时 eta_ratio ≈ 0.667 < 1，永远不可能超过 1。

#### 5.3 所以要给 `HitRecord` 加 `front_face`

    front_face = true    光线从【外侧】射来（空气 → 玻璃）
    front_face = false   光线从【内侧】射来（玻璃 → 空气）

判断方法：

    dot(光线方向, 向外的法线) < 0   →   光线朝里走   →  front_face = true

而且 **`rec.normal` 也要翻到"朝向光线来的一侧"**：

```cpp
void set_face_normal(const Ray& r, const Vec3& outward_normal) {
    front_face = dot(r.direction(), outward_normal) < 0;
    normal     = front_face ? outward_normal : -outward_normal;
}
```

**为什么这不会影响哑光球和金属球？**
因为不透明的球，光线**永远从外侧射来** → `front_face = true` → `normal = outward_normal`，
和原来的行为**一模一样**。只有玻璃（光线能穿进去再出来）才会用到 `front_face = false`。

**看一次完整的"穿过玻璃"，`front_face` 翻了几次：**

    相机射出的光线
      ↓ 第 1 次撞玻璃外壳 ── 从【外侧】打来 → front_face = true
                            → 法线保持朝外（几何外法线）
                            → eta_ratio = 1.0 / 1.5 = 0.667（空气→玻璃）
                            → 折射【进去】
      ↓ 穿过玻璃内部
      ↓ 第 2 次撞玻璃内壁 ── 从【内侧】打来 → front_face = false
                            → 法线【翻转】成朝内（朝向光线来的那一侧）
                            → eta_ratio = 1.5（玻璃→空气）
                            → 折射【出来】
      ↓ 射向天空

> **如果第 2 次还按 `front_face = true` 算**，`eta_ratio` 就会错成 `1/1.5 = 0.667`
> 而不是正确的 `1.5` —— 光线会**拐错方向**，玻璃看起来就不像玻璃了
> （会像一块"贴了玻璃纹理的塑料"）。

**为什么法线也要跟着翻？**
统一让 `rec.normal` 永远**朝向光线来的那一侧**，好处是：

1. 所有材质的代码统一 —— Lambertian/Metal 拿到的法线永远"朝外"，逻辑不用改
2. 折射计算里 `dot(-unit_direction, rec.normal)` 永远是正的余弦（cos θ ≥ 0），
   不用再判断方向

#### 5.4 折射的向量形式（和反射对比着看）

```cpp
inline Vec3 refract(const Vec3& uv, const Vec3& n, double eta_ratio) {
    // ① 入射角的余弦
    double cos_theta = std::fmin(dot(-uv, n), 1.0);

    // ② 折射后的【切向】分量
    Vec3 r_out_perp = eta_ratio * (uv + cos_theta * n);

    // ③ 折射后的【法向】分量
    //    折射光线也必须是单位长度 → |法向| = √(1 − |切向|²)
    Vec3 r_out_parallel = -std::sqrt(std::fabs(1.0 - r_out_perp.length_squared())) * n;

    return r_out_perp + r_out_parallel;
}
```

**和反射对比（这是理解的关键）：**

| | 切向分量 | 法向分量 |
|---|---|---|
| **反射 `reflect`** | **不变** | 翻转（−2(v·n)n） |
| **折射 `refract`** | **按 eta_ratio 缩放** | **重算**（用单位长度约束反推） |

#### 5.5 折射的完整推导（从 Snell 定律推到向量形式）

**目标**：已知单位入射方向 `uv`（指向表面内部）、单位法线 `n`、`eta_ratio`，
求折射方向（也必须是单位向量）。

---

**第 0 步 · 先约定符号**

因为 `uv` 朝里、`n` 朝外，所以 `uv·n < 0`。
定义入射角为 `θ₁`，则：

    cos θ₁ = −(uv·n)          ← 取负号，让它变成正数

`θ₁` 就是"光线与法线的夹角"。

---

**第 1 步 · 和反射一样，把 `uv` 拆成切向 + 法向**

    法向分量 = (uv·n) · n = −cos θ₁ · n
    切向分量 = uv − (uv·n) · n = uv + cos θ₁ · n

**验证"切向分量确实垂直于 n"**：

    dot(uv + cos θ₁ · n,  n) = (uv·n) + cos θ₁ · (n·n)
                              = −cos θ₁ + cos θ₁ · 1
                              = 0                    ✓

**验证"切向分量的长度 = sin θ₁"**：

    |uv + cos θ₁ n|² = |uv|² + 2 cos θ₁ (uv·n) + cos²θ₁ |n|²
                     = 1 − 2 cos²θ₁ + cos²θ₁
                     = 1 − cos²θ₁
                     = sin²θ₁                 ← 勾股定理 sin² + cos² = 1
    所以长度 = sin θ₁                          ✓

> ⭐ **这一步是整个推导的钥匙**：
> **"切向分量的长度" = sin θ。**
> 所以 Snell 定律里对 `sin θ` 的操作，可以直接搬到切向分量上。

---

**第 2 步 · Snell 定律告诉我们切向分量怎么变**

Snell 定律：

    sin θ₂ = eta_ratio · sin θ₁

而切向分量的长度就是 sin θ，所以：

    折射后的切向分量 = eta_ratio × （折射前的切向分量）
                     = eta_ratio × (uv + cos θ₁ · n)

这就是代码里的 `r_out_perp`。

---

**第 3 步 · 法向分量由"折射光线也必须是单位向量"反推**

折射光线也是单位向量：

    |切向|² + |法向|² = 1
    所以 |法向| = √(1 − |切向|²)

方向呢？折射光线跑到表面的**另一侧**，所以法向分量指向 `−n`：

    折射后的法向分量 = −√(1 − |r_out_perp|²) · n

这就是代码里的 `r_out_parallel`。

> **注意这里的设计哲学**：切向分量是 Snell 定律【直接给出】的；
> 法向分量是【被单位长度约束反推】出来的。
> **只要保证整条光线是单位向量，就不用再算一次角度。**

---

**第 4 步 · 合起来**

    折射方向 = r_out_perp + r_out_parallel

---

**第 5 步 · 全反射在数学上"长什么样"**

如果 `eta_ratio × sin θ₁ > 1`，那么 `sin θ₂ > 1` —— 不存在这样的角度。

此时第 3 步里的 `1 − |r_out_perp|²` 会变成**负数**，开根号得到 `NaN`。

所以 `scatter` 里**必须提前判断**，不能等它去开负数：

    bool cannot_refract = eta_ratio * sin_theta > 1.0;

**代码里为什么用 `sqrt(1 − cos²)` 反推 sin？**
因为我们手上只有向量，点积**直接给出** cos（`dot(-uv, n)`），
而"sin"没有直接的向量运算 —— 只能通过 `sin² + cos² = 1` 反推。

---

#### 5.6 三组可验证的数值例子（自己动手核一遍）

以下所有例子都用 `n = (0, 1, 0)`（表面水平，朝上）。

---

**例子 1 · 空气 → 玻璃，光线斜射进来**

    uv = (0.6, −0.8, 0)          eta_ratio = 1.0 / 1.5 = 0.66667

    ① cos θ₁ = −(uv·n) = −(−0.8) = 0.8            → θ₁ = 36.87°
    ② 切向 = uv + 0.8·n = (0.6, −0.8, 0) + (0, 0.8, 0) = (0.6, 0, 0)
       长度 = 0.6 = sin 36.87° ✓
    ③ 折射切向 = 0.66667 × (0.6, 0, 0) = (0.4, 0, 0)
    ④ 折射法向 = −√(1 − 0.4²) · n = −0.91652 · (0, 1, 0) = (0, −0.91652, 0)
    ⑤ 折射方向 = (0.4, −0.91652, 0)

**验证：**

| 检查项 | 计算 | 结果 |
|---|---|---|
| 是单位向量吗 | √(0.4² + 0.91652²) = √(0.16 + 0.84) = √1 | **1** ✓ |
| Snell 定律满足吗 | sin θ₂ = 0.4；eta_ratio × sin θ₁ = 0.66667 × 0.6 = 0.4 | **相等** ✓ |
| 偏向法线了吗 | θ₁ = 36.87° → θ₂ = asin(0.4) = **23.58°** | **变小了** ✓ |

---

**例子 2 · 玻璃 → 空气，同样的角度**

    uv = (0.6, −0.8, 0)          eta_ratio = 1.5

    ① cos θ₁ = 0.8，sin θ₁ = 0.6
    ② 切向 = (0.6, 0, 0)
    ③ 折射切向 = 1.5 × (0.6, 0, 0) = (0.9, 0, 0)
    ④ 折射法向 = −√(1 − 0.81) · n = −0.43589 · (0, 1, 0)
    ⑤ 折射方向 = (0.9, −0.43589, 0)

**验证：**

    sin θ₂ = 0.9   →   θ₂ = 64.16°     ← 比入射角 36.87° 【变大】了（偏离法线）✓

---

**例子 3 · 玻璃 → 空气，角度太大 → 全反射**

    uv = (0.9, −0.43589, 0)       eta_ratio = 1.5

    ① sin θ₁ = 0.9
    ② 判断： eta_ratio × sin θ₁ = 1.5 × 0.9 = 1.35 > 1     ← 出不去！
    ③ 只能走 reflect() 分支

**临界角**：`sin θ_c = 1 / 1.5 = 0.66667` → **θ_c = 41.81°**

> **结论：玻璃内部，入射角超过 41.81° 的光线全部被全反射，一点都出不出去。**
> **这就是光纤的原理** —— 光在纤维里"贴着壁"反复全反射，一路传到另一端。

#### 5.7 代码里的几个细节

- `uv + cos_theta * n` 刚好把法向分量消掉，只剩切向（上面已证明）
- `std::fmin(..., 1.0)` 是**浮点安全**：数学上 `cos θ ≤ 1`，但浮点舍入可能算出 `1.0000000001`，
  那样 `sqrt(1 − cos²)` 会开负数 → `NaN` → 画面上出现黑块
- `std::fabs` 兜底：全反射时 `1 − |切向|²` 是负数，正常流程不会走到（但万一走到了别产生 NaN）

#### 5.8 `Dielectric::scatter` 完整实现

```cpp
attenuation = Color(1.0, 1.0, 1.0);               // 玻璃不吸光

double eta_ratio = rec.front_face ? (1.0 / refraction_index) : refraction_index;

Vec3 unit_direction = unit_vector(r_in.direction());
double cos_theta = std::fmin(dot(-unit_direction, rec.normal), 1.0);
double sin_theta = std::sqrt(1.0 - cos_theta * cos_theta);

bool cannot_refract = eta_ratio * sin_theta > 1.0;

Vec3 direction = cannot_refract
               ? reflect(unit_direction, rec.normal)
               : refract(unit_direction, rec.normal, eta_ratio);

scattered = Ray(rec.p, direction);
return true;
```

### 原理 6 · 递归深度限制（今天最重要的一课）

#### 6.1 事故

加上玻璃球之后，程序**崩溃**了：

    exit code = 0xC00000FD     ← Windows 的 STATUS_STACK_OVERFLOW（栈溢出）

而且是**部分渲染之后**崩的（扫描线跑到 148/225）。

#### 6.2 为什么会栈溢出（推理链 + 量化估算）

**推理链：**

    ray_color 是递归的
       ↓
    唯一出口 = "光线射向天空"
       ↓
    ★ 颜色的衰减【不会】终止递归！
      return attenuation * ray_color(scattered, world);
      先【完整算完】递归，再乘 attenuation —— 递归层数一层都不会少
      衰减只影响"结果多暗"，不影响"递归多深"
       ↓
    以前没炸：哑光/金属的弹射是递减的，且随机方向很快飞向天空
       ↓
    玻璃：attenuation = (1,1,1) 【完全不衰减】
         且全反射会把光线"关"在球里来回弹
       ↓
    每层递归压一帧栈 → 栈耗尽 → 崩溃

**量化估算一下"栈有多浅"：**

| 项目 | 数值 |
|---|---|
| Windows 主线程默认栈大小 | **1 MB**（约 1,048,576 字节） |
| 一层 `ray_color` 栈帧的大小 | 局部变量 `HitRecord`（3 个 double + bool + shared_ptr ≈ 40 B）<br>+ `Ray scattered`、`Color attenuation`（各 24 B）<br>+ 参数、返回地址、对齐填充<br>≈ **150～250 字节** |
| 所以最多能递归多少层 | 1,048,576 ÷ 200 ≈ **约 5000 层** |

**但我们的程序崩在第 148 行扫描线**（总共 225 行）——
说明**某些光线的递归深度超过了 5000 层**。这和"全反射把光困在玻璃里"的分析吻合。

**⚠️ 而且这是个"运气"问题**：崩不崩取决于随机数。可能这次崩、下次不崩、换个分辨率又崩。
**所以不能靠"跑两次没崩"来判断它没问题。**

**怎么识别这类崩溃：**

| 症状 | 含义 |
|---|---|
| 退出码 `0xC00000FD` | Windows 的 `STATUS_STACK_OVERFLOW` |
| 退出码 `-1073741571` | 同上（有符号形式） |
| **部分渲染之后**突然死掉 | 递归走到某一根光线才炸的典型特征 |
| 一跑就崩（还没开始渲染） | 多半不是栈溢出，是别的（比如数组越界） |

#### 6.3 修复

```cpp
Color ray_color(const Ray& r, const Hittable& world, int depth) {
    if (depth <= 0) return Color(0, 0, 0);    // ★ 保险丝，必须在最前面
    ...
        return attenuation * ray_color(scattered, world, depth - 1);
    ...
}
```

`main` 里：`const int max_depth = 50;` → `ray_color(r, world, max_depth)`

#### 6.4 为什么这不是"作弊"

1. **物理上**：真实世界的光线确实会衰减殆尽那，50 次弹射后颜色早衰减到人眼分辨不出
2. **工程上**：没有深度限制的渲染器**随时可能崩**（两面平行镜子之间会无限来回弹）
   —— 和"循环必须有终止条件"是同一个道理

> **教训**：
> **"物理上会衰减"不等于"代码会终止"。**
> 递归/循环的终止条件必须是**结构性保证**（`depth <= 0`），
> 不能依赖"数值迟早会变小"。

#### 6.5 `max_depth` 不同取值的现象

| `max_depth` | 现象 |
|---|---|
| 1 | 只有直接看到的东西，几乎没有间接光，画面很暗 |
| 2 | 只有一次弹射 |
| 5 | 已经比较像样了 |
| 50 | 和无限深度几乎看不出区别（RTIOW 用 50） |
| 1000 | 又慢又没意义 |

### C++ 技能点（今天新学）

#### 1. `override` 关键字 —— 强烈建议每次覆盖虚函数都写

```cpp
bool scatter(...) const override { ... }
```

`override` 让**编译器帮你检查**："你确定这是覆盖基类的虚函数吗？"
签名写错一个字（比如忘 `const`），编译器会**报错**而不是悄悄创建一个新函数。

**不写 `override` 的话，这种错误编译器不会告诉你** —— 症状是"运行时材质完全没生效"，极难查。

#### 2. `shared_ptr` 与 `make_shared`

```cpp
std::make_shared<Lambertian>(Color(0.9, 0.3, 0.3))
//                  ↑ 类型        ↑ 传给构造函数的参数
```

`make_shared<T>(args...)`：
1. 在堆上创建 `T` 对象（用 `args` 调构造函数）
2. 返回管理它的 `shared_ptr`

比 `shared_ptr<T>(new T(args))` 更好：**内存分配只有一次**（控制块和对象放一起），更快也更安全。

#### 3. 在 `HitRecord` 里存 `shared_ptr<Material>` 而不是 `Material*`

1. **共享**：一个材质可以给多个球用（100 个球同一块大理石）
2. **生命周期**：`shared_ptr` 用引用计数自动管理，最后一个持有者销毁时才释放
3. **安全**：裸指针容易忘记释放（泄漏）或悬空（use-after-free）

#### 4. 前向声明解决**循环包含**

- `material.h` 需要 `HitRecord`（作为函数参数）
- `hittable.h` 的 `HitRecord` 需要 `Material`（作为成员）
- **互相 include 会死循环**

解法：`material.h` 只用**前向声明**：

```cpp
struct HitRecord;   // 只告诉编译器"有这么个类型"，不给出内容
```

**什么时候够用？**
- 用作**引用 / 指针** → 够用 ✅
- 需要访问**它的成员**（`rec.normal`）→ 不够，需要完整定义 ❌

所以 `material.h` 前向声明即可；`lambertian.h` 要读 `rec.normal`，就必须 `#include "hittable.h"`。

#### 5. 三元运算符 `条件 ? 值A : 值B`

```cpp
fuzz(fuzz < 1 ? fuzz : 1)
double eta_ratio = rec.front_face ? (1.0 / refraction_index) : refraction_index;
```

**用途**：初始化列表里没法写 `if`，三元运算符是唯一选择。

#### 6. `std::fmin` / `std::fabs` —— 浮点专用版本

| 函数 | 作用 |
|---|---|
| `std::fmin(a, b)` | 返回较小的（浮点安全，处理 NaN、−0） |
| `std::fabs(x)` | 浮点绝对值 |

#### 7. 成员的**声明顺序 = 初始化顺序**

```cpp
private:
    Point3 center;
    double radius;                    // ← 先声明
    std::shared_ptr<Material> mat;    // ← 后声明
```

**实际初始化顺序由"声明顺序"决定，而不是初始化列表里写的顺序。**
两边不一致 → 编译器报 `[-Wreorder]` 警告。

当前代码里无害（成员互不依赖），但如果是 `: b(a + 1), a(2)` 这种**有依赖**的写法就会真出错。
**养成习惯：成员声明顺序 = 初始化列表顺序。**

#### 8. `struct` 也可以有方法

`HitRecord` 不再只是"一堆字段"，现在有了行为（`set_face_normal`）。
**struct 和 class 在 C++ 里只差默认访问权限**（struct 默认 public，class 默认 private）。

### 今天踩的坑（比知识更值钱）

1. **`return = 0.5 * (...)`** —— `return` 是关键字不是变量，后面不能有 `=`。
   （起因是我表述有歧义："把 `color =` 改成 `return`"。）

2. **`pixel_color += ray_color(...)` 写了两次** —— 采样循环跑 8 次却累积 16 次，
   最后只除以 8 → 颜色变成 2 倍（过曝）。
   **记这个模式：「累积了多少次」和「除以多少」必须严格一致。**

3. **函数定义在 `main` 里面** → `a function-definition is not allowed here`。

4. **`Color pixel_color` 声明在错误的层级** → `was not declared in this scope`。
   自查方法："这行代码是**每个像素**执行一次，还是**每行**执行一次？"

5. **变量名复用导致遮蔽** —— 采样循环的计数器又用了 `i`、`j`。
   **采样循环的计数器应该用 `s`。**

6. **手滑输入 `{=========`** —— 文件里多了一串等号，编译器报了一堆莫名其妙的错误。

7. **⭐ `rec` 被自动补全改成了 `recv`**
   编译器曾提示 `'rec' was not declared in this scope; did you mean 'recv'?`，
   然后 `recv` 就真的出现在了代码里。
   **`recv` 是 C 标准库的"网络套接字接收"函数名**，和我们的 `HitRecord rec` 毫无关系 ——
   编译器只是按**字符串相似度**瞎猜的。

   > **两条铁律**：
   > 1. **永远不要盲目接受编译器的 "did you mean" 建议**
   > 2. VS Code 弹出自动补全（灰色幽灵文字）时，**按 Esc 取消，不要按 Tab 接受**，除非你确认那就是你要的

8. **场景被覆盖** —— 想"加"一个玻璃球，结果把金属球**改成了**玻璃球。
   而且注释写着"放在 x = -1"，坐标却是 `(1, 0, -1)`。
   **教训：改场景时对照注释和坐标，别只看注释。**

9. **文件被"并发编辑"搞乱** —— 工具改文件的同时，编辑器里有未保存内容，
   结果产生"注释和半行代码拼在一起"的垃圾。

   > **工作流规则**：
   > 1. 让工具改文件之前，先 <kbd>Ctrl</kbd>+<kbd>S</kbd> 保存
   > 2. VS Code 提示"文件已在磁盘上更改"时，选"覆盖/重新加载"，别选错
   > 3. 改完立刻编译一次，能最早发现这类混乱

10. **⭐ 栈溢出崩溃（`0xC00000FD`）** —— 见"原理 6"，今天最有价值的一课。

11. **"编译成功"的假象** —— `cmd1; cmd2` 在 PowerShell 里不管前者成败都会继续，
    导致"编译失败但跑的是旧 exe"。（Day 3 的坑，今天用 `run.ps1` 已经根治）

### 判据总结（怎么快速判断"图变了没有"）

| 工具 | 敏感度 | 用途 |
|---|---|---|
| 文件**时间戳** | —— | 判断"有没有重新生成" |
| **PPM** 文件大小 | ❌ 低 | 只反映"数字位数"，颜色变了位数没变时**大小不变** |
| **PNG** 文件大小 | ✅ 高 | 对内容敏感，可以当"变了没变"的快速判据 |
| **抠具体像素值** | ✅ 最高 | 小数量变化时的唯一可靠手段 |
| **单元测试** | ✅✅ | 最终的解决方案（还没写） |

**实例**：某次改动后 PNG 大小**和上次一字不差**（120,509 B），
立刻断定"图根本没变" —— 一查果然是场景没改。
